pktSNMP Administration

Deployment, configuration, and maintenance reference for system administrators.

Architecture Overview

pktSNMP is a single systemd service combining a FastAPI backend, background workers, and a React SPA — all running on one server with no required external dependencies beyond Python.

│  ├── SNMP trap receiver  (UDP 162, asyncio)          │
│  ├── Local poll engine   (pysnmp, asyncio)           │
│  ├── Alert engine        (60s loop)                  │

Prerequisites

On the server: Python 3.11+, Node.js 20+ via NVM (for frontend builds), Git.

Optional: ClickHouse server (only if switching the storage backend from SQLite).

⚠️

Build on the server, not Windows. The frontend node_modules directory contains Linux-native binaries. Always build on the target server — never on a Windows workstation.

Fresh Install

1
Clone the repository on the server 
ssh -i your-key.pem user@YOUR-SERVER-IP
cd /mnt/software
git clone git@github.com:your-org/pktsnmp.git pktsnmp
cd pktsnmp
2
Create a Python virtual environment 
python3 -m venv venv
source venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
3
Create config.yaml 
cp config.example.yaml config.yaml

Edit at minimum: set secret_key (generate with openssl rand -hex 32), db_path, and log_file.

4
Run database migrations

Migrations run automatically at startup. To apply manually:

source venv/bin/activate
python -c "from app.database import run_migrations; import asyncio; asyncio.run(run_migrations())"
5
Install and start the systemd service 
sudo cp pktsnmp.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable pktsnmp
sudo systemctl start pktsnmp
6
Build and deploy the frontend

See the Frontend Build section below.

7
First login

Browse to http://YOUR-SERVER-IP:8767. Log in with the default admin credentials and change the password immediately.

Frontend Build & Deploy

The frontend must be built on the server — the node_modules tree contains OS-specific binaries.

Automated (recommended)

From your workstation, run the deploy script from scripts/. It uploads changed files and triggers a build + service restart on the server via SSH/Paramiko.

Manual (on the server)

cd /mnt/software/pktsnmp/frontend
source ~/.nvm/nvm.sh
nvm use 20
npm ci
npm run build
sudo systemctl restart pktsnmp

The built output lands in frontend/dist/ and is served by FastAPI's StaticFiles mount.

Collector Setup

pktSNMP receives SNMP data two ways: via its built-in local poll engine, and via remote OpenTelemetry Collector (otelcol) instances that push OTLP HTTP data.

Local Collector

Runs in-process. Enable via Settings → SNMP in the UI. Polls all devices assigned collector_id=1 and listens on UDP 162 for traps. Requires AmbientCapabilities=CAP_NET_BIND_SERVICE (already set in the service file).

Remote otelcol Collector

Deploy an otelcol-contrib instance at each remote site. Add the following exporter block to your otelcol config:

exporters:
  otlphttp/pktsnmp:
    endpoint: "http://YOUR-SERVER-IP:8767/api/snmp/ingest/otlp"
    headers:
      Authorization: "Bearer YOUR_COLLECTOR_TOKEN"
    tls:
      insecure: true
    timeout: 30s
ℹ️

Path note: otelcol appends /v1/metrics to the endpoint automatically. The actual POST hits /api/snmp/ingest/otlp/v1/metrics. Both paths are registered.

Metric Naming Convention

The SNMP parser expects metric names prefixed with SNMP/:

SNMP/<SITE>/<DEVICE>/<OID_LABEL>
# e.g. SNMP/SITE-A/CORE-SW1/ifInOctets

Metrics not prefixed with SNMP/ are ignored. Configure your otelcol SNMP receiver metrics: block to use this naming scheme.

Device Registration

For proper device resolution, set the otelcol_label field on each device record in the UI to match the path segment in the metric name (e.g., SITE-A/CORE-SW1). When matched, the device's last_seen and status are updated automatically on each ingest batch.

Collector Token

Generate a bearer token in Collectors → [collector name] → Rotate Token. Update the otelcol config on the remote host and restart otelcol after rotating.

Auth & SAML

Local Auth

Default admin credentials are set during installation. Change via Settings → Users or the key icon in the sidebar. JWT access tokens expire in 15 minutes; httpOnly refresh cookies last 7 days.

SAML 2.0 (Okta or compatible IdP)

Configure in Settings → Auth:

1
Set IdP metadata in pktSNMP

Enter the Entity ID, SSO URL, and paste the IdP certificate in Settings → Auth.

2
Create a SAML app in your IdP

ACS URL: https://YOUR-FQDN:8767/api/auth/saml/callback
Audience URI: https://YOUR-FQDN:8767/api/auth/saml/metadata
Name ID format: EmailAddress

3
Add a role attribute statement

Name: role, Value: user's app-level role (admin / analyst / viewer).

🔒

HTTPS required for SAML. The ACS URL must use the same hostname as your TLS certificate. HTTP is not supported for SAML callback.

Alert Engine

The alert engine runs as a background task, evaluating all enabled rules every 60 seconds (with a 15-second startup delay). It auto-fires and auto-resolves based on current device and metric state.

Firing Behavior

When a rule fires: an event is inserted in alert_events, devices.status is set to 'down' (for device-level rules), and notifications are dispatched. Cooldown prevents re-firing if an open event already exists within the cooldown window (default 30 min).

Resolving Behavior

When the condition clears: devices.status is set to 'up' and resolved_at is set on all open events for that rule + device.

Notification Channels

Configure channels in Settings → Alerts → Notification Channels. Supported: inapp, email, slack, pagerduty, webhook.

Storage Backends

Switch backends via Settings → Storage in the UI. Restart the service after switching — the backend is read from SQLite at startup.

BackendBest forConfig
SQLite (default)Most deployments — zero external dependency, easy backupAutomatic — no setup needed
ClickHouseVery high-volume environments or long-term retention at scaleSet host/database in config.yaml; requires a running ClickHouse server
⚠️

Data is not migrated when switching backends. Existing time-series data stays in the old store. Plan backend selection before ingesting production data.

Backup & Restore

Automated Backup

Configure schedule and retention in Settings → Backup. Trigger immediately via the UI or API:

curl -X POST http://YOUR-SERVER-IP:8767/api/system/backup \
  -H "Authorization: Bearer YOUR_TOKEN"

Manual Backup

# Stop service first if snmp_timeseries.db has active writes
sudo systemctl stop pktsnmp
cp /mnt/software/pktsnmp/pktsnmp.db \
   /mnt/software/pktsnmp_backups/pktsnmp_$(date +%Y%m%d_%H%M%S).db
cp /mnt/software/pktsnmp/snmp_timeseries.db \
   /mnt/software/pktsnmp_backups/snmp_timeseries_$(date +%Y%m%d_%H%M%S).db
sudo systemctl start pktsnmp

Restore

sudo systemctl stop pktsnmp
cp /mnt/software/pktsnmp_backups/pktsnmp_<timestamp>.db \
   /mnt/software/pktsnmp/pktsnmp.db
cp /mnt/software/pktsnmp_backups/snmp_timeseries_<timestamp>.db \
   /mnt/software/pktsnmp/snmp_timeseries.db
sudo systemctl start pktsnmp

Upgrading

Run the deploy script from your workstation, or manually on the server:

cd /mnt/software/pktsnmp
git pull
source venv/bin/activate
pip install -r requirements.txt   # if requirements changed
cd frontend
source ~/.nvm/nvm.sh && nvm use 20
npm ci
npm run build
sudo systemctl restart pktsnmp

Database migrations run automatically on startup. No manual schema steps are needed unless noted in individual migration file comments.
