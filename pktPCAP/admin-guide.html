Installation

1. Clone the Repository

git clone git@github.com:<your-org>/pktpcap.git /opt/pktpcap

2. Create a Python Virtual Environment

cd /opt/pktpcap
python3 -m venv venv
# Install packages using the virtualenv pip explicitly
./venv/bin/python -m pip install -r service/requirements.txt
⚠️

Always install packages using ./venv/bin/python -m pip install rather than calling the pip binary directly. If multiple Python environments are present on the host, the pip shebang may point to the wrong interpreter.

3. Place SSL Certificates

Create the ssl/ directory at the root of the installation and place your certificate and private key there:

mkdir -p /opt/pktpcap/ssl
cp /path/to/your/server.crt /opt/pktpcap/ssl/server.crt
cp /path/to/your/server.key /opt/pktpcap/ssl/server.key
chmod 600 /opt/pktpcap/ssl/server.key

SSL is auto-detected on startup based solely on file presence. No configuration toggle is needed. See the SSL section for more detail.

4. Initialize the Database

Start the server once manually to let it initialize the SQLite database and generate the secret key:

cd /opt/pktpcap/service
../venv/bin/python server.py

Confirm it starts cleanly, then stop it (Ctrl+C) and proceed to the systemd setup.

systemd Service

pktPCAP runs as a managed systemd service for automatic start on boot and supervised restart on failure.

Service Unit File

# /etc/systemd/system/pktpcap.service
[Unit]
Description=pktPCAP Packet Capture Analysis Platform
After=network.target

[Service]
Type=simple
User=your-service-user
WorkingDirectory=/opt/pktpcap/service
ExecStart=/opt/pktpcap/venv/bin/python server.py
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Enable and Start

sudo systemctl daemon-reload
sudo systemctl enable pktpcap
sudo systemctl start pktpcap
sudo systemctl status pktpcap

SSL / TLS Configuration

pktPCAP enforces HTTPS. TLS is activated automatically when certificate files are detected at startup — there is no database toggle or environment variable required.

Certificate Paths

FilePathDescription
Certificatessl/server.crtPEM-format certificate (or chain)
Private Keyssl/server.keyPEM-format private key

Both paths are relative to the repository root. If either file is missing on startup, the server falls back to HTTP — avoid this in production.

Converting a PFX/P12 Certificate

If your certificate is in PKCS#12 format (exported from a Windows certificate store or provided by your CA), convert it to PEM with:

# Extract the certificate
openssl pkcs12 -in your-cert.pfx -nokeys -out ssl/server.crt

# Extract the private key
openssl pkcs12 -in your-cert.pfx -nocerts -nodes -out ssl/server.key
🚨

Protect the private key file. Set permissions to 600 and ensure it is owned by the service user. Never commit it to version control.

Certificate Renewal

Replace the files at ssl/server.crt and ssl/server.key in place, then restart the service to pick up the new certificate:

sudo systemctl restart pktpcap

Authentication

pktPCAP supports two authentication methods that can be used simultaneously:

  • Local Authentication: Username and password stored in the SQLite database (bcrypt hashed). Managed from the Settings panel.
  • SAML 2.0 SSO: Enterprise identity provider integration (see SSO section).

Authentication state is maintained via server-side Flask sessions. All sessions are invalidated on logout or service restart.

SAML SSO Configuration (Okta)

pktPCAP integrates with SAML 2.0 identity providers using the python3-saml library. The following steps document the configuration for Okta, but the process is similar for any SAML-compliant IdP.

⚠️

python3-saml must be installed in the pktPCAP virtualenv for SSO to be available. The Settings panel will show whether SAML is active. If it shows as unavailable, install it: ./venv/bin/python -m pip install python3-saml

1. Create an Okta App Integration

  1. In Okta Admin, go to Applications → Create App Integration → SAML 2.0.
  2. Set the Single Sign-On URL to: https://<your-server>:<port>/api/auth/saml/callback
  3. Set the Audience URI (SP Entity ID) to: https://<your-server>:<port>/api/auth/saml/metadata
  4. Under Attribute Statements, add an attribute named role mapped to appuser.Role if you want role sync on every login.

2. Configure pktPCAP Settings

In the pktPCAP Settings panel (Admins only), navigate to SSO / SAML Settings and populate:

FieldValue
IdP Entity IDFrom Okta app → Sign On → SAML Setup (Issuer)
IdP SSO URLFrom Okta app → Sign On → SAML Setup (Identity Provider Single Sign-On URL)
IdP CertificateThe X.509 certificate from Okta (download from app settings)
SP Entity IDhttps://<your-server>:<port>/api/auth/saml/metadata

3. First Login Behavior

When a user authenticates via SSO for the first time, pktPCAP automatically provisions their account. If Okta sends a role attribute, the user is assigned that role. If no role attribute is sent, the user is assigned the Admin role by default — adjust this in the Settings panel post-provision if needed.

4. Role Sync

On every subsequent SSO login, pktPCAP reads the role attribute (if present) from Okta and syncs it to the local user record. This allows role changes to be managed centrally in Okta without requiring administrator action in pktPCAP.

Service Provider Metadata

The SP metadata XML is available at: /api/auth/saml/metadata — provide this URL to your IdP during app setup if it supports metadata import.

User Management

User accounts are managed from the Settings → Users panel, accessible only to Admins.

Creating a User

  1. Navigate to Settings → Users → Add User.
  2. Enter username, email address, and initial password.
  3. Assign a role (Admin, Analyst, or Viewer).
  4. Set status to Active and save.

Editing a User

Click any user row to edit their username, email, role, or status. Changes take effect on their next login (active sessions are not immediately terminated).

Resetting a Password

Use the Reset Password action on the user row to set a new password. The user will need to sign in with the new credentials — SSO users do not use passwords.

Deactivating a User

Set a user's status to Inactive to prevent login without deleting their account and history. This is the recommended approach for offboarded users.

Settings Panel

The Settings panel (/settings) is only accessible to Admin-role users. It provides a web-based interface for all configuration tasks described in this guide, including:

  • User and role management
  • AI provider API key and model selection
  • SAML SSO configuration
  • Application log viewer and log-level control
  • Service restart button
  • SSL status display

AI Provider Configuration

pktPCAP supports two AI backends. Configure your preferred provider from Settings → AI Configuration.

OpenAI

Provide your OpenAI API key and select the desired model (e.g., gpt-4o, gpt-4-turbo). The key is stored encrypted in the database and never exposed to the browser.

Anthropic Claude

Provide your Anthropic API key and select the model (e.g., claude-sonnet-4-5). Configuration is identical to OpenAI.

ℹ️

Only structured packet metadata and analyst queries are sent to the AI provider API. Raw packet bytes, payload contents, and capture files are never transmitted — all parsing happens locally on the server.

Testing the AI Connection

Use the Test Connection button in Settings → AI Configuration to send a minimal probe request and confirm the API key and model are valid before analysts begin using the platform.

Logs & Monitoring

Application logs are viewable directly in the Settings panel. Logs include request activity, authentication events, analysis jobs, errors, and service lifecycle events.

Clearing Logs

Logs can be cleared from the Settings panel. This removes all stored log entries from the database — it does not affect journald system logs.

Troubleshooting

Service won't start

Check the journal for detailed error output: sudo journalctl -u pktpcap -n 50 --no-pager. Common causes:

  • Python module missing — run ./venv/bin/python -m pip install -r service/requirements.txt
  • Port already in use — check with ss -tlnp | grep 8765
  • SSL cert missing or malformed — confirm files exist at ssl/server.crt and ssl/server.key

SAML SSO login fails with "Invalid Response"

  • Verify the SP Entity ID in your IdP matches exactly (including port number and trailing path).
  • Confirm the IdP certificate in pktPCAP Settings matches the current signing certificate in your IdP.
  • Check that your server's clock is synchronized — SAML assertions have a short validity window and clock skew causes validation failures.

AI analysis returns an error

  • Verify the API key is valid and has not expired — use Test Connection in Settings.
  • Confirm the server has outbound internet access to the AI provider endpoint.
  • Check the log viewer in Settings for the specific error message from the AI API.

Live feed not appearing after running the tshark command

  • Confirm the feed token embedded in the command is current — regenerate it from the Live Feeds page if needed.
  • Verify the remote host can reach the pktPCAP server on the configured port.
  • Check that tshark is installed on the remote host: tshark --version
  • Confirm the capture interface name is correct for the remote host — interfaces vary by OS and configuration.

Large file uploads time out

If very large captures fail to upload, the issue is typically a client-side or reverse-proxy timeout. If pktPCAP is behind a load balancer or reverse proxy, increase the upstream timeout. For very large captures, consider pre-filtering with Wireshark or tshark to reduce file size before uploading.

pktHub Integration

pktPCAP integrates with pktHub — the unified management hub — allowing users to access pktPCAP through pktHub's reverse proxy without a separate login. Authentication is handled automatically via a suite token that pktPCAP generates and pktHub presents on every proxied request.

Getting the Suite Token

  1. Open pktPCAP and navigate to Settings → Integrations.
  2. Scroll to the pktHub Integration card.
  3. Click Reveal to view the token, then Copy to copy it to your clipboard.
  4. If no token exists yet, one is generated automatically on first visit.

Registering pktPCAP in pktHub

  1. In pktHub, navigate to Settings → App Registry.
  2. Click Register App.
  3. Fill in:
    • App Name: pktPCAP
    • Base URL: https://<host>:8765
    • Suite Token: paste the token you copied from pktPCAP
    • Hub Return URL: same as Base URL (optional)
  4. Click Register. pktHub calls /api/health to verify connectivity, then stores the token.

How the Proxy Auth Works

When a user opens pktPCAP through pktHub's proxy, pktHub automatically includes the X-Suite-Token header on every request. pktPCAP's before_request hook validates the token against its stored value. If it matches, the user is authenticated as the pktHub user (X-Suite-User and X-Suite-Role headers) without needing to log in separately.

Regenerating the Suite Token

If you need to revoke pktHub's access to pktPCAP (e.g., for a security rotation), use the Regen button in Settings → Integrations → pktHub Integration. This generates a new token immediately — the old token stops working. You must then re-register pktPCAP in pktHub with the new token.

⚠️

Important: After regenerating the token, pktPCAP will appear as degraded in pktHub until you re-register with the new token. Existing user sessions through the proxy will stop working immediately.

Health Monitoring

pktHub polls GET /api/health on pktPCAP every 30 seconds. This endpoint is public (no authentication required) and returns:

{"status": "ok", "app": "pktpcap", "version": "0.1.0"}

A 200 response marks pktPCAP as healthy. Any other response marks it degraded.
